태양광 매칭 AI 오케스트레이터 사전 설계

자연어 리드 추출 → Tool Calling 오케스트레이션 → Streamlit 데모 UI. 3주 안에 production 확장이 가능한 아키텍처로 단단히 설계하고, RAG·다채널 입력·추가 Tool을 무수정으로 얹을 수 있는 인터페이스를 미리 깔아둡니다.

제안자 권혁 (12년차 풀스택) 예산 500만원 (VAT 별도, 정부지원사업) 기간 3주 스택 Python · FastAPI · LangChain · GPT-4o · Streamlit

1. 한줄 요약

발주사가 제공하는 매칭/수익 코어 엔진 API를 신뢰하고, 그 위에서 자연어 → 구조화 → 보완 질문 → 다중 Tool 오케스트레이션 → 합성 응답의 6단계 파이프라인을 짭니다. 단순 데모가 아니라 다음 단계에서 RAG·여러 LLM 공급자·다채널(웹/카카오톡/이메일)로 확장할 때 코어를 다시 짤 필요가 없는 형태로 설계합니다.

"시니어 레벨로 3주 이내에 핵심 아키텍처를 단단하게"라는 우대 사항에 정확히 부합하는 구성으로 제안합니다.

3. 모듈 상세 설계

3-1. 모듈 1 — 리드 추출 (Lead Extractor)

사용자의 한 문장에서 핵심 정보 6개를 Pydantic schema로 추출. 필수 누락 시 자연스러운 보완 질문을 생성합니다.

from pydantic import BaseModel, Field
from typing import Optional, Literal

class SolarLead(BaseModel):
    region:       Optional[str]   = Field(None, description="시/군/구 또는 위경도")
    capacity_kw:  Optional[float] = Field(None, description="발전 용량 kW")
    install_type: Optional[Literal["roof", "ground", "carport"]] = None
    budget_won:   Optional[int]   = None
    timeline:     Optional[str]   = Field(None, description="착공 희망 시점")
    purpose:      Optional[Literal["self_use", "sell_to_grid", "hybrid"]] = None

class ExtractionResult(BaseModel):
    lead: SolarLead
    missing_required: list[str]       # 누락 필수 필드
    clarification: Optional[str]      # 다음 보완 질문
    confidence: float

예시 입력 → 출력

사용자 발화추출 결과
"용인쪽 공장 옥상에 200kW 정도 올리고 싶은데 자금은 3억쯤이에요" region=용인, capacity_kw=200, install_type=roof, budget_won=3억 · missing: [timeline, purpose] · clarification: "착공 희망 시점과, 발전 전력 사용 목적(자가소비/판매)을 알려주실 수 있을까요?"
"태양광 좀 알아보고 있어요" 전부 null · clarification: "어느 지역에 어떤 규모로 검토 중이신가요? 옥상/노지 등 설치 위치와 대략적인 용량(kW)을 알려주시면 도움 드리기 수월합니다."

3-2. 모듈 3 — 오케스트레이터 (Tool Calling)

구조화된 리드를 받아 GPT-4o의 Function Calling으로 다음 4개 tool을 상황에 맞게 호출합니다.

tools = [
  {
    "name": "solar_match_api",
    "description": "발주사 매칭 엔진. 리드 정보로 적합 시공사 점수화 결과 반환",
    "parameters": { "region": "str", "capacity_kw": "float", "install_type": "str" }
  },
  {
    "name": "revenue_estimate_api",
    "description": "발주사 수익 계산기. 위치·용량·일사량으로 예상 연수익 산출",
    "parameters": { "region": "str", "capacity_kw": "float", "irradiance_kwh_m2": "float" }
  },
  {
    "name": "public_irradiance",
    "description": "기상청/한전 공공 일사량 데이터 조회. 지역 입력 시 연간 평균 일사량 반환",
    "parameters": { "region": "str" }
  },
  {
    "name": "kb_search",                              // Dummy / 확장 인터페이스
    "description": "지식베이스 검색. 향후 RAG 연동 시 활성화",
    "parameters": { "query": "str" }
  }
]

전형적 호출 시퀀스

1. orchestrator(lead)
2.   → tool_call: public_irradiance(region="용인")
3.   ← { irradiance: 1340 }
4.   → tool_call: revenue_estimate_api(region="용인", capacity_kw=200, irradiance_kwh_m2=1340)
5.   ← { annual_revenue_krw: 38_000_000, payback_years: 7.8 }
6.   → tool_call: solar_match_api(region="용인", capacity_kw=200, install_type="roof")
7.   ← { matches: [...3 contractors with scores...] }
8. synthesize(...) → "용인 지역 옥상형 200kW, 예상 연수익 3,800만원..."

4. 비기능 요구사항 대응

요구사항설계
공공 API 지연 시 Fallback tool 호출은 asyncio.wait_for(timeout=3s). 타임아웃 시 LLM에게 "공공 일사량을 받지 못함, 추정치 사용"을 알리고 보수적 기본값 1100 kWh/m² 으로 계속 진행
Langfuse 모니터링 OpenAI 호출·tool 호출·총 토큰·지연·비용을 trace ID 단위로 묶어 자동 기록. 매 세션 URL을 Streamlit 디버그 패널에 노출
매칭 엔진과 무관 매칭/수익 계산은 발주사 API에 위임. 본 시스템은 호출자(orchestrator)만 책임
RAG 사전 세팅 tool kb_search Dummy 등록 + 인터페이스 정의만 완료. 향후 RAG 인덱스 추가 시 핸들러만 교체
다채널 확장 FastAPI Gateway가 단일 진입점 → Streamlit/카카오톡/이메일 봇이 모두 동일 endpoint 사용

5. 3주 일정

주차산출물
1주차 발주사 매칭/수익 API 명세 협의 · 리드 추출 모듈 + 보완질문 루프 · Pydantic schema 확정 · Langfuse 연결
2주차 Orchestrator(Tool Calling) · 공공 일사량 API 어댑터 · Fallback 정책 · 합성 응답 프롬프트
3주차 Streamlit UI · 통합 테스트 · 대화 시나리오 5종 회귀 · 운영 매뉴얼 · API 명세서 작성 · 이관
