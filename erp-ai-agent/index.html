UNIERP 구매 자동화 AI Agent 무결성 설계

UNIERP에 데이터를 입력하더라도 기존 ERP의 회계 무결성을 절대 해치지 않는 안전한 연계 방안과, LangGraph 기반 AI Agent 워크플로, 사람이 끊을 수 있는 승인 게이트, 감사로그 설계를 미리 제시합니다.

제안자 권혁 (12년차 풀스택) 예산 2,000만원 (협의 가능 명시) 기간 4개월 스택 Python · FastAPI · Celery · LangGraph · Langfuse · Next.js · MSSQL · PostgreSQL

1. 한줄 요약

발주사가 제안서에 명시한 "ERP 무결성을 해치지 않는 안전한 연계 방안"이 본 프로젝트의 가장 큰 리스크라고 봅니다. 직접 INSERT 방식은 처음 한 번의 사고로 회계 결산이 무너질 수 있어 권장하지 않으며, Staging Table + 사람이 끊는 승인 게이트 + 감사로그의 3중 방어 구조를 제안합니다.

"비용 조율 가능, 수행 가능한 금액으로 지원" 명시. 본 설계의 범위와 안전장치를 검토하신 후 합리적 견적을 함께 협의 드립니다.

2. ERP 연계 방식 3안 비교

방식무결성속도유지보수본 프로젝트 적합도
① Direct DB Insert
(UNIERP 테이블 직접 쓰기)		 매우 위험 빠름 ERP 버전업 시 매번 깨짐 ❌
② Staging Table + 승인
(별도 테이블 → 사람 승인 → ERP 표준 SP 호출)		 안전 중간 스키마 캡슐화로 안정 ⭐ 권장
③ RPA (UNIERP 화면 자동조작) 화면 변경에 취약 느림 UI 변경마다 깨짐 △ 백업 옵션

본 제안은 ②번 Staging Table 패턴을 기본으로 하고, UNIERP가 제공하는 표준 API/SP가 있으면 그것을 우선 사용합니다. ②번이 불가능한 모듈(예: 특수 전표)만 ③RPA를 백업으로 사용합니다.

3. 무결성 3중 방어 설계

// 데이터 흐름 (회계 전표 자동 등록 예시)

[AI Agent / 사용자 명령]
       │
       ▼
[App DB (PostgreSQL)]                           // 1차 영역
  ┌─────────────────────────────────────────┐
  │ vendor_closing_draft  (마감 초안)        │
  │ vendor_response_match (회신 대사 결과)   │
  │ tax_invoice_parsed    (세금계산서 파싱)  │
  │ erp_staging_journal   (전표 적재 대기)   │   ← 승인 전 상태
  └─────────────────────────────────────────┘
       │
       │ ★ 담당자가 화면에서 "ERP 등록" 클릭 (승인 게이트)
       ▼
[Audit Log]                                     // 2차 영역
  ┌─────────────────────────────────────────┐
  │ who · when · what · before · after       │
  │ idempotency_key (UUID)                   │   ← 중복 등록 방어
  │ erp_response (성공/실패 응답 원문)        │
  └─────────────────────────────────────────┘
       │
       ▼
[UNIERP (MSSQL)]                                // 3차 영역, ERP 정본
  ┌─────────────────────────────────────────┐
  │ EXEC dbo.usp_RegisterPurchaseInvoice ... │   ← ERP 표준 SP 사용
  │  → 실패 시 자동 롤백, App DB에 실패 마킹  │
  │  → 성공 시 ERP 트랜잭션 ID 회수해 저장    │
  └─────────────────────────────────────────┘
핵심 원칙 ① ERP 정본은 절대 직접 쓰기 금지 ② App DB에 모든 중간 상태 보존 ③ 사람 승인 게이트 통과 시에만 ERP SP 호출 ④ 멱등성 키로 중복 등록 차단 ⑤ ERP 응답 원문을 감사 로그에 기록

5. AI Agent Tool 정의 (요약)

Tool역할안전 등급
query_unierp(sql)UNIERP 읽기 전용 조회. 화이트리스트 view만 허용read-only
vendor_lookup(name)App DB 거래처 마스터 조회read-only
render_excel_template(data)기존 양식 그대로 엑셀 생성local
smtp_send(to, subject, body, attach)업체별 마감 메일 발송 (BCC로 관리자 포함)외부 영향
diff_excel(original, returned)수량·단가·금액·부가세 자동 대사local
ocr_invoice(file)세금계산서 PDF/이미지 파싱local
exec_unierp_sp(sp_name, params)UNIERP 표준 SP 호출. 화이트리스트 SP만 허용쓰기 (승인 후)
render_report(template, data, fmt)2~3 페이지 PPT/PDF 자동 생성local

핵심 원칙: 쓰기 권한(exec_unierp_sp)은 LLM이 자동으로 호출할 수 없도록 워크플로 그래프 상에서 사람 승인 노드 통과 후에만 활성화합니다. LLM이 단독으로 회계 전표를 만들 수 없는 구조입니다.

6. 감사로그 스키마

CREATE TABLE audit_log (
  id                BIGSERIAL PRIMARY KEY,
  ts                TIMESTAMPTZ NOT NULL DEFAULT now(),
  actor_type        TEXT      NOT NULL,   -- 'user' | 'agent' | 'system'
  actor_id          TEXT,                  -- user.id 또는 agent run_id
  action            TEXT      NOT NULL,   -- 'send_mail', 'post_invoice', ...
  target_type       TEXT,                  -- 'vendor', 'invoice', 'erp_journal'
  target_id         TEXT,
  payload_before    JSONB,                 -- 변경 전 상태
  payload_after     JSONB,                 -- 변경 후 상태
  idempotency_key   UUID UNIQUE,           -- 중복 실행 차단
  erp_response      TEXT,                  -- ERP 호출 시 원문 응답
  langfuse_trace_id TEXT                   -- LLM 추적 ID 연결
);

9. 리스크 고지

이 프로젝트가 안고 있는 본질적 리스크
  • UNIERP 표준 API/SP 가용성 — 표준 호출 인터페이스가 부족하면 RPA(③) 백업안으로 일부 우회. 미팅 시 UNIERP 운영팀과 합동 확인 필요
  • 세금계산서 OCR 정확도 — 국세청 전자세금계산서 XML이 가능하면 OCR 대신 XML 파싱으로 100% 정확도 확보 가능. 우선 협의 권장
  • 업체 회신 엑셀 양식 통일성 — 업체마다 다르면 정규화 비용 증가. 초기에 표준 양식 강제 정책 권장
  • 회계 결산 일정과의 충돌 — 운영 중 ERP는 결산 기간 잠금이 걸리므로 배포 윈도우를 발주사 회계팀과 사전 협의해야 함
